# GAME_PLAN — «Своя игра» (online Jeopardy, 2–6 игроков)

## 1. Цель и сценарий

Онлайн-игра «Своя игра» (формат Jeopardy) на существующем стеке сайта
football-draft: 2–6 игроков в приватной комнате, общие вопросы с доски.
Два режима: **25 вопросов** (5 категорий × 5 номиналов) и **15 вопросов**
(3 категории × 5 номиналов) — режим выбирает хост перед стартом.
Номиналы: 500/1000/1500/2000/2500. Серверный таймер, начисление ± очков,
таблица результатов с обработкой ничьей.

### Состояния комнаты (единый автомат)
```
LOBBY ──(хост, ≥2 игроков)──> BOARD
BOARD ──(выбор ячейки)──> QUESTION
QUESTION ──(ответ/таймаут)──> REVEAL
REVEAL ──(все видели ответ)──> BOARD (следующий ход)  |  FINISHED (доска пуста)
```
Дополнительно: любой игрок может выйти в LOBBY (результаты сохранены,
комната живёт). Хост может закрыть игру досрочно (FINISHED).

## 2. Архитектура — почему Supabase (а не отдельный Socket.IO сервис)

**Решение: переиспользуем существующий паттерн Supabase Realtime + Postgres.**

Обоснование:
1. Сайт задеплоен на **Vercel** (serverless): отдельный Node-процесс с
   Socket.IO здесь работать не может — нет long-running хоста, state между
   инстансами не переживает деплой. Это задокументировано как следствие:
   при рестарте/колде-старте инстанса состояние берётся из Postgres, и всё
   продолжается.
2. В проекте **уже есть** три реализованных онлайн-игры на Supabase Realtime
   (`quiz_rooms`, `geo_rooms`, cs2 battle rooms) — та же схема:
   - Postgres-таблица комнаты как **single source of truth**;
   - Realtime-канал на `postgres_changes` (фильтр `id=eq.<roomId>`);
   - **polling каждые ~1 c** как страховка от потерянных событий;
   - **серверный таймер** — колонка `next_at timestamptz`: любой клиент,
     видящий просроченный `next_at`, продвигает фазу (идемпототентно).
3. Все мутации идут через Supabase REST (RLS «anyone can update») —
   защита от гонок и подделок строится **в игровом движке** (чистая функция
   `applyAction`), который проверяет права актора и состояние фазы ДО записи.

### Single source of truth
- **БД**: вся игровая комната (доска, игроки, очки, текущий вопрос, фазы,
  таймер, порядок ходов) — в таблице `svoya_rooms` (jsonb).
- **Вопросы**: статический TS-модуль `question-sets.ts` (импортируется и
  в движок, и в UI) + `validateBoard()` — проверка структуры, уникальности,
  полноты доски.
- **Ответ**: `answer` — **текст** игрока; вердикт `correct: boolean` выносит
  **хост** (как в настоящей «Своей игре» ведущий). Для вопросов с
  однозначным фактом хост отвечает «верно/неверно». Если хост не ответил
  за 30 с — автоматический вердикт: точное совпадение с эталоном
  (нормализация: регистр, пробелы, пунктуация). Это закрывает кейс
  «игрок должен угадать правильно», но без подмены хостом.

### Таймер
- Ответ: **20 с** (настраивается хостом в лобби: 10/20/30/60).
- REVEAL: **10 с** до следующего хода.
- Все `next_at` — ISO-время, пишет тот, кто продвинул фазу; отрисовка
  клиента идёт от `next_at` (а не локальный setTimeout) → одинаково на
  всех клиентах.

### Порядок ходов (turn order)
- Очередь = порядок входа в комнату (стабильный, хранится в БД).
- Каждый игрок по очереди: выбирает вопрос → ход переходит следующему.
- После REVEAL ход снова в очередь (следующий игрок).
- Если игрок выбыл/перезагрузил — его позиция в очереди сохраняется
  (id-based), очередь не ломается.

### Безопасность (что проверяет движок на каждой мутации)
| Атака | Защита |
|---|---|
| Двойной выбор ячейки | `applyAction` проверяет `board[c][r].taken` + фаза BOARD |
| Двойной ответ на вопрос | поле `currentAnswer.submitted` в БД |
| Ответ после дедлайна | `next_at` + check фазы QUESTION (read-then-write) |
| Подделка очков | очки **только** движок считает в `applyAction` и пишет целиком |
| Действие не со своим ходом | очередь ходов + `turnPlayerId` в БД |
| Чужие admin-действия | только `isHost`-поле в players (хост) |
| Подделка room code | код — только для **нахождения** комнаты; права — по `playerId` |
| Гонки | read-then-write на свежее состояние + идемпотентные продвижения |

### Передача хоста (deterministic)
Если хост покинул комнату: новый хост = **первый по порядку входа**
оставшийся игрок. Правило детерминированно — один и тот же результат
на любом клиенте. В лобби видна кнопка «Передать хоста» (текущий хост
может явно передать другому).

## 3. Модели данных

### `SvoyaRoom` (Postgres: `svoya_rooms`)
```ts
{
  id: string;            // uuid
  code: string;          // 5 символов (A-Z2-9 без похожих)
  status: "lobby" | "board" | "question" | "reveal" | "finished";
  hostId: string;
  answerSeconds: number; // 20 по умолчанию
  mode: 15 | 25;         // режим: 15 или 25 вопросов (по умолчанию 25)
  seed: number;
  players: Player[];     // [{id, name, isHost, joinedAt}]
  board: Cell[];         // 15 или 25 ячеек: {cat, value, qId, taken, takenBy}
  scores: Record<playerId, number>;
  turnQueue: string[];   // порядок ходов (playerId)
  turnIndex: number;     // чей сейчас ход
  current: { cat: number, val: number, qId: string,
             pickedBy: string, answers: Record<playerId, {optionId, correct}> } | null;
  nextAt: string | null; // серверный таймер
  createdAt: string;
}
```

### Вопросы (`questions.ts`)
Категории: `football`, `cs2`, `movies`, `music`, `geo`, `history`,
`kazakhstan`, `mixed`. 8 категорий × 5 вопросов (номиналы
500/1000/1500/2000/2500) = 40 вопросов. Режим 25 → 5 категорий,
режим 15 → 3 категории (выбираются случайно при создании комнаты).
Структура:
```ts
{ id, cat, value, q, options: string[4], answer: string[], explanation: string }
```
`options[0]` — всегда правильный ответ (движок определяет вердикт по
индексу). `validateQuestions` гарантирует: все id уникальны,
каждая категория × номинал есть, текст не пустой, ответ ≥1 вариант,
ровно 4 опции, options[0] соответствует answer[0].
Аудит всех вопросов: `QUESTION_AUDIT.md`.

## 6. Риски и ограничения

- **Supabase-зависимость**: без `NEXT_PUBLIC_SUPABASE_URL` игра не
  работает (как и все онлайн-игры проекта). Оффлайн-режима нет — это
  ограничение онлайн-формата.
- **Realtime-задержка**: на корпоративном прокси (squid) realtime идёт
  через `/api/proxy/supabase-ws` — задержка может быть выше; polling 1 c
  страхует.
- **Хост-вердикт**: если хост не верифицирует ответ, игра может
  «зависнуть» на REVEAL — решено таймаутом авто-вердикта (30 с).
- **Vercel**: нет long-running — любой «зависший» таймер продвигает
  первый активный клиент (идемпотентно). Это осознанное ограничение
  serverless-архитектуры, задокументировано.
- **Ничья**: два+ игрока с одинаковым максимумом — все получают пометку
  «🏆» и XP `win` (честно, без подброса случайного).

## 8. Ручная 2-браузерная проверка (инструкция)

Требования: включённая сеть до `*.supabase.co`, применённый
`supabase/svoya-schema.sql` (Supabase SQL Editor), `NEXT_PUBLIC_SUPABASE_URL`
и `NEXT_PUBLIC_SUPABASE_ANON_KEY` в `.env.local`.

```
1. npm run dev  (http://localhost:3000)
2. Вкладка А: /svoya → имя «Хост» → СОЗДАТЬ КОМНАТУ.
   Появляется код (5 символов) и ссылка-приглашение /svoya/join/<КОД>.
3. Вкладка Б (или другое устройство/вкладка инкогнито): открыть
   /svoya/join/<КОД> → имя «Игрок2» → ВОЙТИ. Оба видят лобби с 2 игроками.
4. Вкладка А: таймер ответа 20 с → НАЧАТЬ ИГРУ. Доска 5×5 видна обеим.
5. Ход А: выбрать ячейку → вопрос виден обеим, таймер 20 с.
   Вкладка Б отвечает текстом → хост (А) ставит ВЕРНО/НЕВЕРНО.
   Проверяем: очки +/−, REVEAL с пояснением, ход перешёл к Игроку2.
6. Таймаут: выбрать ячейку и не отвечать 20 с → авто-прогресс
   (−номинал выбранному), вопрос не засчитан.
7. Проверить, что не-хост не может ставить вердикт, а не-текущий игрок не
   может выбрать чужую ячейку (кнопки неактивны).
8. Дожать доску до пустой → TABLICa результатов, ничья = все 🏆.
9. Перезагрузить вкладку Б → «С возвращением», игрок возвращается в комнату.
```
